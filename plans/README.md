## Before you dispatch anything — worktree base precondition

The SSH-transport precondition that used to live here is gone: that slice was
discarded and the native companion was deleted by plan 006. The working tree is
clean as of `b11f485`.

The live precondition is **branch stacking**. Executor subagents run in isolated
git worktrees created from `main` by default, and worktrees contain only
committed files. Plans 009 and 010 both build on the module plan 008 creates,
so each must be branched from `advisor/008-inventory-v2-types`, not from `main`.
Both carry a base check as their first instruction and will stop rather than
run against the wrong base.

Recommended sequence for the schema-v2 slice: run **008** alone, review and
merge it, then run **009** and **010** in parallel from it.

  Running them out of order produces a conflict.

- **002 is independent of all others** but gated on the SSH slice being

  `src/core/inventory-v2.ts`. They do not depend on each other and touch no

## What these plans do not cover

The audit produced roughly 25 vetted findings; these five are the highest-leverage
subset plus the one strategic decision. Deliberately not planned yet, in rough
priority order:

- `git` inherits the full process environment in the Go host, and
  `GIT_CONFIG_COUNT` is set only on the authenticated path, so an inherited
  `GIT_CONFIG_*` set applies on every SSH and unauthenticated operation
  (`gittransport/git.go:67-81`).
- Every capture re-stamps `generatedAt` and every item's `observedAt`, so every
  Git commit is 100% diff noise and the no-op short-circuit at `git.go:260` is
  unreachable.
- Remote-controlled `sourceUrl` is rendered as an anchor with no scheme
  validation (`options/main.tsx:578`; unvalidated at `inventory.ts:145-155`).
- Every failed `git push` is reported as a conflict, masking auth failures and
  timeouts (`git.go:284-285`).
- Changing the native Git remote orphans a live token in the OS keyring and
  removes the only UI that could delete it (`native-git-store.ts:7-15`).
- Six config-loading effects drop their rejections, rendering configured
  backends as unconfigured with a blank error banner (`options/main.tsx:111-174`).
- Credentialed `fetch` calls follow redirects; `x-amz-security-token` is not
  stripped cross-origin (no `redirect:` option in any of the four backends).
- Backend duplication has already drifted — HTTP 423 is a conflict on Gitea
  (`gitea.ts:111`) and a server error on GitHub (`github.ts:110`).
- Branch/path/size validation exists in Go but is absent in TypeScript, and the
  README claims Gitea branch validation that does not exist.
- README claims guided restore works; three of seven control-center nav links
  are dead anchors; the `alarms` permission is declared with no consumer.
- No LICENSE file — a public repository described as FOSS is all-rights-reserved
  by default.
- Zero test coverage on the message router, all five service wrappers, and
  `ExecRunner` (the code that hands credentials to `git`).
- The 1089-line `App()` re-renders the full extension list on every keystroke.
- SigV4 canonical-query ordering and encoding are wrong but currently
  unreachable, since no call site passes query parameters (`sigv4.ts:55,60`).
- `maxInventorySize` (768 KiB) base64-encodes to exactly `MaxMessageSize`
  (1 MiB), so a near-maximum inventory exceeds the frame limit and terminates
  the host process.
- Broken `npm install` onboarding path, no lint/formatter, no `CLAUDE.md`,
  missing WebDAV setup guide, unused `@types/chrome`.

## Findings considered and rejected

- **"The message listener returns a Promise, which Chromium ignores"** — this was
  ranked finding #1 in the 2026-08-31 audit, assessed as making the extension
  non-functional on its primary target. **It is wrong.** The claim rested on
  Chrome's long-standing documented contract (a listener must call
  `sendResponse` and `return true`; a returned Promise is ignored) plus reading
  `@wxt-dev/browser`, which resolves `browser` to `chrome` on Chromium with no
  polyfill. Plan 003's Step 1 required empirical confirmation before any change.
  Executed against real Chromium 151.0.7922.173 with the unpacked build driven
  over the DevTools Protocol, every message round trip **succeeded**: the popup
  rendered correct data with no console errors, and a direct
  `chrome.runtime.sendMessage({type:'inventory:get'})` returned
  `{"ok":true,"inventory":{...}}` — including after clearing storage to rule out
  stale data. Modern Chromium honors a Promise returned from
  `runtime.onMessage`. No change was applied; plan 003 is REJECTED. The
  historical Chrome behavior is real, so this is worth re-checking if the
  project ever needs to support older Chromium builds — but it is not a defect
  today.

- **Round-trip inequality from the three divergent sort orders** — real
  (`captureInventory` and `parseInventoryJson` sort by name-then-id,
  `serializeInventory` by `browserFamily:id`) but low impact: serialization
  re-canonicalizes on every write, so the bytes are stable, and
  `diffInventories` is Map-keyed, so comparison is order-independent. Pinned by
  a characterization test in plan 005 rather than treated as a defect.
- **Pinning WXT exactly / adopting PLAN.md's workspace layout** — the caret on a
  `0.x` package already admits only `0.21.x`, so the pin buys little; and eight
  workspace packages for a 6K-LOC single-artifact extension would cost more than
  the flat layout it replaced. The document is the stale half here, not the tree.
- **Coverage thresholds** — pointless until the untested router/service layer is
  covered; would go red on day one with nothing actionable behind it.
- **Deleting `sync`/`getStatus`/`cancel` from the protocol schema's command
  enum** — the schema matches the `Command` constants declared in
  `message.go:14-16`; they are declared but unhandled. Whether they should exist
  is a maintainer question about intent, not a mechanical cleanup, so plan 002
  leaves them alone deliberately.
- **Adding `webextension-polyfill` to fix the Chromium message bug** — it would
  work, but it changes the runtime for every extension API in the project. Plan
  003 takes the three-line adapter instead.

## Step 2 (plans 011-014): the actual data-loss fix

These four are a strict chain — each one's base check refuses to run without its
predecessor merged. Run them one at a time, reviewing between.

- **011** writes the merge algorithm as a pure function. Nothing calls it.
- **012** wraps it in fetch/write/retry against the `InventoryBackend` interface,
  plus the explicit one-way v1->v2 upgrade. Still nothing calls it; no service
  changes.
- **013** is where user-visible behavior finally changes: the four services stop
  overwriting. Services keep returning a projected v1 `InventoryDocument`, which
  is why `entrypoints/` needs no edits at all — that is what plan 010 bought.
- **014** adds the UI action that lets a user convert an existing remote, which
  is what makes the fix reachable. Deliberately last: it is a one-way door.

After 014, `PLAN.md`'s Milestone 2 exit condition is met. Cross-browser identity
resolution, pruning, and encryption remain out.

## Follow-ups opened by plans 008-010

- **Worktree provisioning lands executors on a stale base.** All three executors
  were provisioned at `2f8fe62` — the deleted native-companion line — rather than
  current `main`. Each caught it only because its plan carried an explicit base
  check and the dispatch told it to re-branch. Keep that check in every future
  stacked plan.
- **`liftV1ToV2` builds its extensions map with `Object.fromEntries`**, so a
  duplicate minted id would silently overwrite a record rather than fail. Moot
  with `crypto.randomUUID()`, but a caller injecting a colliding generator would
  lose extensions quietly.
- **v1 has two canonical orders**: `parseInventoryJson` sorts by `name` then `id`
  while `serializeInventory` sorts by `browserFamily:id`, so a v1 parse ->
  serialize round trip reorders the array. Pre-existing and harmless today;
  relevant to anyone byte-comparing v1 documents.
- **Cross-family comparison is still broken, deliberately.** `diffInventories`
  keys on `browserFamily:id`, so an extension aliased across families appears on
  both sides of the diff. `tests/inventory-projection.test.ts` pins this current
  behavior with a comment rather than hiding it. Fixing it means implementing the
  identity ladder in `docs/design/inventory-schema-v2.md` §3.
- **Still required before v2 can ship to users**: the merge algorithm (§4), the
  "Upgrade to multi-device inventory" action (§5), the service/UI cutover, and
  pruning (§4). Until those land, `INVENTORY_SCHEMA_VERSION` stays 1 and every
  backend still writes v1.
